# План реализации Lapis

Статус актуален на август 2026 года. Локальный launcher, API и серверный Fabric Bridge уже образуют рабочий вертикальный срез: пользователь входит в Lapis, устанавливает нужную сборку и попадает на защищённый сервер.

## Выполнено

### Учётные записи и сессии

- pnpm-монорепозиторий, NestJS/Fastify API, Prisma и PostgreSQL Compose.
- Регистрация, вход, обновление и выход из сессии.
- Zod-валидация: ник — 3–16 латинских символов, цифр или `_`; пароль при регистрации — минимум 6 символов.
- Argon2id для паролей, HMAC-хеши refresh-токенов, ротация refresh-токенов и JWT access-токены.
- Refresh-токен никогда не передаётся renderer-процессу Electron: он хранится через Windows `safeStorage`.
- Восстановление сессии после перезапуска launcher; временная недоступность API не удаляет локальную сессию.
- e2e-тесты auth API.
- Production Docker deployment: API доступен через `https://lapis-mc.ru/api`, работает за HAProxy/Nginx/HTTPS, использует изолированный PostgreSQL volume, health checks, runtime migrations и rate limit для auth.
- Публичные URL и URL контента формируются из одной production-константы; домены не хранятся в таблице модов. Переход на `api.lapis-mc.ru` потребует только замены конфигурации после публикации DNS и сертификата.

### Каталог и интерфейс launcher

- Каталог серверов со статусом и количеством игроков; отдельный worker обновляет статусы.
- Клик по статусу открывает список игроков с головами из их Lapis-скинов; worker получает имена через стандартный Minecraft Status Protocol в уже существующем 30-секундном цикле без дополнительного фонового опроса.
- Основной экран с серверной иконкой, статусом, меню действий и полосой прогресса установки.
- Количество модов открывает модальное окно с составом сборки; действие удаления скрыто, пока локальной сборки нет.
- Единые компоненты бренда, иконок-кнопок, уведомлений и модальных окон.
- Настройки запуска на сборку: лимит ОЗУ и полноэкранный режим, сохранённые локально в профиле launcher.
- Экран профиля с 3D-моделью скина и загрузкой пользовательского PNG-скина.
- Velopack updater для Windows: обязательная startup-проверка, автоматическое delta-first обновление, редкий фоновый scheduler, модальное управление уже открытого launcher и безопасная установка после закрытия Minecraft.
- Update hardening: single-instance, проверка диска, быстрый и отложенный retry, pending-restart recovery и безопасное восстановление процесса Minecraft по PID плюс времени создания.

### Сборки и запуск Minecraft

- Изолированные сборки в `%USERPROFILE%\.lapis\instances\<build-id>`.
- Java 25, Minecraft, Fabric, библиотеки, assets и обязательные моды скачиваются и проверяются по SHA-1.
- Установка сообщает этап и ограниченный по частоте прогресс для Java, Minecraft, библиотек, assets, Fabric и каждого мода; для модов показываются имя и счётчик загруженных файлов.
- Перед загрузкой Java/сборки проверяется свободное место. Обновление launcher выполняет отдельную проверку места перед передачей управления Velopack; первичный Velopack Setup использует системную проверку установщика.
- Подписанный Ed25519 install-manifest: renderer не выбирает версии, пути или URL файлов.
- Одна активная игра на launcher. Состояние синхронизируется с Java-процессом, включая внешнее завершение процесса.
- Loader ждёт фактической инициализации Minecraft по новому `latest.log`, а не только старта Java.
- Автоподключение к выбранному серверу после готовности клиента.
- Основной сервер `main` закреплён на `195.208.129.43:25565` и использует обязательный Lapis Bridge ticket-flow: launcher получает одноразовый билет API, передаёт его клиентскому Bridge только через локальный bootstrap, а серверный Bridge связывает билет с точным ником Lapis-профиля.
- Клиентский Lapis Bridge является системным модом лаунчера: он собирается из `fabric-bridge`, входит в release resources, заменяет каталоговую копию перед проверкой сборки и автоматически принимает обязательный ресурспак управляемого сервера без повторного окна согласия.
- Loopback bootstrap работает до фактического завершения Minecraft и выдаёт отдельный короткоживущий одноразовый билет для каждой новой попытки подключения. Повторный ручной вход в сервер в рамках той же JVM не использует уже погашенный билет и не требует перезапуска игры.
- Закрытие окна лаунчера во время работающей игры только скрывает UI: main-процесс и ticket-bootstrap остаются активны. Повторный запуск ярлыка показывает то же окно, а после завершения JVM скрытый launcher закрывается автоматически.

### Авторизация в игре и скины

- Одноразовый игровой билет на 60 секунд, хранимый API только как HMAC-хеш.
- Клиентский и серверный Fabric Bridge: сервер не принимает подключение без валидного билета.
- Локальный одноразовый loopback bootstrap между launcher и клиентским Bridge.
- Интеграция загрузки скинов через MineSkin v2 с ограничением размера PNG, очередью и rate limit.
- Подписанные свойства MineSkin хранятся в PostgreSQL по неизменяемому `userId`; регистр ника больше не создаёт отдельную запись скина. Старые JSON-файлы SkinRestorer читаются и лениво мигрируют для обратной совместимости.
- Серверный Bridge `0.1.4+` запрашивает подписанный скин вместе с погашением одноразового игрового билета и сохраняет его через публичное хранилище SkinRestorer до завершения входа. Дополнительного фонового опроса и повторной загрузки через MineSkin нет; ошибка скина не блокирует авторизацию.
- API сохраняет совместимость со старым Bridge: расширенный ответ включается только при заявленной capability `signed-skin-v1`, поэтому Bridge и API можно обновлять поэтапно.

### Основа администрирования

- Масштабируемый RBAC с отдельными ролями, permissions, глобальными/server-scoped назначениями и audit events.
- Системная роль `super_admin` имеет все текущие и будущие права; первый администратор назначается существующему пользователю только локальной CLI-командой.
- Глобальная проверка access token и permissions в API; `/v1/me` возвращает capabilities, защищённый `/v1/admin/servers` — полный read-only список серверов.
- Access token больше не передаётся Electron renderer: обычные и административные запросы выполняет main process через узкие IPC-методы.
- В launcher доступен первый закрытый экран администрирования со списком серверов. Детальный статус — `docs/admin-platform-plan.md`.
- Для UI-разработки Vite-страница работает в обычном браузере через dev-only bridge к локальному API; production Electron по-прежнему использует только preload IPC.
- Реализован client-only срез администрирования: создание сервера с отдельной копией клиентской сборки, изменение адреса/порта/видимости, streaming-загрузка клиентского JAR, переключение и массовое удаление модов с подтверждением.
- Информация сервера и моды открываются отдельными явными действиями в строке. Адаптивное окно модов имеет закреплённую панель добавления/выбора/удаления; новый JAR появляется сверху выключенным, а повторная загрузка того же имени заменяет версию с сохранением состояния. API ограниченно читает `fabric.mod.json` и показывает совместимость с Minecraft/Fabric без сетевого или фонового опроса. Физические файлы новых версий хранятся по SHA-1 с обратной совместимостью legacy-путей.
- Выключенные моды исключаются из подписанного manifest; перед запуском launcher приводит каталог `mods` выделенной instance к точному составу manifest, включая удаление лишних локальных JAR. Остальные пользовательские данные instance не затрагиваются.

## Следующий этап

1. **Надёжность запуска и UX.** Ручная проверка первого чистого скачивания с новым поэтапным прогрессом, тайм-аутов и внешнего завершения Minecraft; добавить понятную диагностику, если клиент завершился до окна.
2. **Управление сборками.** Версии и каналы сборок, миграции конфигураций и управляемая очистка пользовательских файлов поверх уже готовых проверки места и экрана состава модов.
3. **Операционная часть сервера.** Завершить ручную проверку загрузки скина после обновления Bridge и перезапуска Minecraft-сервера; затем добавить health-check API/worker, ротацию ключей, резервные копии БД и серверных конфигураций.
4. **Production hardening.** CI, GitHub Release и HTTPS-feed работают; требуется завершить ручной acceptance test Velopack 0.1.3 → 0.1.4 и заменить self-signed подпись публично доверенным Code Signing/Azure Artifact Signing. Затем добавить аудит логов без секретов и резервные копии. Детальный статус — `docs/velopack-migration-status.md`.
5. **Администрирование.** Провести ручной тест client-only среза, включая выключенное состояние нового мода, совместимость, массовое удаление и строгую синхронизацию у клиента. Затем добавить архивацию серверов, безопасный сбор неиспользуемых CAS blobs, отображение audit trail и только после подтверждения перейти к неизменяемым ревизиям и server-side составу. Поэтапная архитектура и критерии проверки зафиксированы в `docs/admin-platform-plan.md`.
6. **Качество.** Интеграционные тесты IPC/launch-потока и ручной smoke-набор для Windows, Java, установки, login, скинов и Bridge.

## Границы и правила

- Production-ключи и API-ключ MineSkin не хранятся в репозитории; используйте локальные `.env`, исключённые из Git.
- Лаунчер не должен удалять игровую сборку, сессию или пользовательские файлы без явного подтверждения.
- При недоступности API сохранённая сессия остаётся на устройстве; пользователь видит ошибку доступности, а не принудительный logout.
